# Atlas Context Engine

**Sprint:** 7.4
**Date:** 2026-08-25
**Status:** Implemented, deterministic, and AI-free.

## Purpose

Context answers a practical question: **Can this Task be completed with what is
available here and now?** It is an execution constraint, not an Area, Project,
status, tag, schedule, or ranking generated by Atlas.

The built-in vocabulary is:

```text
Computer · Phone · Home · RV · Lab · Errands · Calls · Anywhere
```

Users may add short custom values while editing or triaging a Task. A Task may
have zero, one, or several contexts. Zero contexts means no known restriction;
`Anywhere` explicitly communicates the same eligibility.

## Dependency flow

```text
Task editor / Inbox triage
  -> TaskFeature or InboxFeature
  -> TaskService or InboxService
  -> createTask()
  -> normalizeContexts()
  -> ItemRepository -> Prisma -> PostgreSQL contexts[]

Workspace filters
  -> WorkspaceFeature.loadWorkspace(filters)
  -> WorkspaceService
  -> filterTasksByContext()
  -> render-ready Today / Scheduled projection
```

`src/domain/ContextEngine.ts` is pure TypeScript. It imports no React, Next.js,
repository, Prisma, browser, network, or AI code. The UI collects criteria and
renders the result; it never filters Task data itself.

## Domain rules

- Built-in names normalize case-insensitively, so `@computer`, `COMPUTER`, and
  `Computer` become `Computer`.
- Leading `@`, surrounding whitespace, and repeated internal whitespace are
  normalized.
- Duplicate values are removed case-insensitively while preserving the first
  custom spelling.
- One context may contain at most 80 characters.
- An unconstrained Task is eligible in every selected context.
- A Task with `Anywhere` is eligible in every selected context.
- Otherwise, at least one assigned context must match the selected context.
- Combined filters use AND semantics and preserve repository order.
- Energy and duration filters are maximum available capacity, not exact values.
- A Task without an estimate is excluded when a duration maximum is active;
  Atlas cannot honestly claim that unknown work fits.

Workspace supports one active value for each of Context, Area, Project, Energy,
Duration, and Status. The domain contract can be extended to sets later without
changing Task persistence.

## Compatibility and persistence

`Task.contexts` is canonical. `context` and `preferredContext` remain populated
with the first canonical value so existing Planner and stored-data consumers do
not break during the compatibility window. Reads can still derive one context
from those legacy fields when an older in-memory Item lacks `contexts`.

Migration `20260825190000_context_engine` adds a non-null PostgreSQL `TEXT[]`
column and copies the existing preferred or legacy context into its first
element. It creates no Areas, Projects, Tasks, or placeholder data. Its rollback
copies the first array value back before dropping the new column.

Custom contexts are deliberately Task-owned strings rather than separate
records. This keeps creation fast and avoids another repository. The tradeoff is
that a custom context with no remaining Tasks disappears from Workspace filter
options. A future saved-context catalogue would be a separate product decision.

## Workspace behavior

Filters apply only to Pinned, Today, and Scheduled Task collections. The Project
rail remains complete because active outcomes must stay continuously visible.
Filter options are assembled before filtering, so choosing a narrow result does
not make other options disappear.

The form submits intentionally instead of querying on every keystroke. This
keeps server-backed filtering predictable on mobile and keyboard accessible.
Clear returns to the unfiltered projection. No filter changes persistence.

## Planning compatibility

The deterministic Planning Rules Engine now recognizes any matching Task
context. A Task with explicit `Anywhere` matches every current context; an
unconstrained Task stays eligible but receives no explicit context-match bonus.
No Task is scheduled, moved, or changed by this rule.

## Non-goals

- location tracking or geofencing;
- inferred contexts;
- AI classification;
- automatic scheduling;
- a global custom-context settings screen;
- changing Area or Project ownership.
